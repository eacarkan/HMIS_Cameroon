## 2. Cross-cutting verification

- **No live external calls by default (egress-safe).** Every external touch-point routes through an **adapter** (`lib/integration/adapter.ts`): `MockIntegrationConnector` makes no network call; `resolveConnectorAdapter` returns the mock for MOCK/SANDBOX and **always throws** `IntegrationLiveDisabledError` for `PRODUCTION_DISABLED`; the live flag `HMIS_INTEGRATION_LIVE_ENABLED` defaults **off**. 4A, 4B (mock API) and 4D (mock confirm) each carry a **network-egress guard test** that spies on `globalThis.fetch` and asserts **zero** calls. No UI → external direct calls (adapter-mediated only).
- **Credential references only — never secrets.** `IntegrationCredentialReference` stores a *pointer* (env-var name / vault path), and `looksLikeSecret`/`validateCredentialReference` reject anything resembling a literal secret; the privacy scan finds no committed secrets.
- **Staging is never clinical (4C).** An imported external result lands in a **staging** table; a diagnostics reviewer (**≠ the importer**) promotes it through the **existing Phase 2I** `enterDiagnosticResultTx`, so the result is **still hidden from clinicians until a separate validator validates it** (import ≠ review ≠ validate — three distinct actors). The doctor-visibility invariant was adversarially confirmed to hold, and a wrong-patient promotion gap was found and fixed pre-commit.
- **A mock payment confirmation never marks an invoice paid (4D).** Confirmation is a guarded status transition through the mock connector; the **only** way money reaches an invoice is **reconciliation**, which delegates to the already-hardened Phase 2C/3 `recordPayment` (amount-validated, `InvoiceItem`-snapshot-preserving, audited). 4D writes no invoice/payment rows directly.
- **Insurance is manual (4E).** No insurer API, no auto-adjudication, no automatic claim submission; the claim and pre-auth state machines are forward-only and guarded (`SUBMITTED_PLACEHOLDER` is a human status). Eligibility is a labelled placeholder ("aucune vérification assureur réelle"). A claim may reference an invoice only for the **same patient** as the coverage.
- **Analytics is aggregate-only, no patient-level, no AI (4F).** Reports are built **exclusively** from the Phase 2E aggregate operational report (proven nominative-free by the privacy scan), transformed by a pure function that can only emit whitelisted aggregate keys, and passed through `assertAggregateReportRows` before persistence **and** export. **No cross-hospital analytics path** — the Phase 3D rule that `central.aggregate.view` is the sole cross-hospital capability, reading snapshots only, is preserved.
- **Hospital scoping + per-hospital server-side RBAC + audit — everywhere.** Every 4A–4F read/write is hospital-scoped at the DB layer (`findFirst { id, hospitalId }`, composite-unique upserts, guarded `updateMany`); every mutating service calls `requireCapability(actor, ctx, cap)` resolving `actor.rolesByHospital[ctx.hospitalId]` (never the cross-hospital union); cross-hospital attempts are denied; all integration/finance/insurance/analytics actions are appended to the audit log with actor + hospital. New capabilities are held by the **non-clinical** `administrateur` (integration/finance/analytics admin), `caissier` (finance), `directeur` (oversight read), and `technicien_diagnostic` (result review) — clinical roles hold none of them.
- **Adversarial reviews caught & fixed real defects before commit.** 4C — wrong-patient promotion (a mismatched patient/order was still stored as `matchedOrderId`) → fixed at import + re-verified at promote, regression test added. 4E — two cross-entity integrity gaps: a cross-payer coverage-profile link, and a wrong-patient claim/invoice binding → both rejected, regression test added. 4A/4B/4D/4F relied on directly-tested guarantees (egress guard, aggregate-only assertion, confirm-never-pays) in lieu of a separate adversarial pass.
